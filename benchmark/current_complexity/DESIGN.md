Use Google Benchmark's actual `Complexity(oAuto)` functionality to characterize finite-range scaling of the frozen **eighth-sampling experimental KKT** and the unchanged retained-edge Borůvka comparator. This is not a new implementation repair, an all-six ranking experiment, a crossover claim, or an asymptotic proof. The retained-edge comparator uses the same contraction helper and no sampling/verifier.

They cannot answer this revision's scaling question and must not be pooled with the new measurements. ## Frozen proposal matrix

One process measures one algorithm/family/graph-seed/sampling-seed curve. Families are `leaf_hierarchy4` at m=32n, its identical-topology `leaf_shuffled4` control at m=32n, and `gnm_random` at m=16n. Each uses the complete fixed ladder

`n = 1024, 2048, 4096, 8192, 16384, 32768, 65536, 131072, 262144, 524288, 1048576`.

The minimum avoids the hierarchy generator's dense-core capacity limit. Each fit uses `N=n+m` from the actual generated record count; densities are never mixed under one fitted curve. Along each fixed-density ladder N is proportional to n, so this does not independently identify n and m dependence or establish a uniform two-parameter bound.

Declare two fresh graph seeds and two fresh sampling seeds after a scoped source search and review, before any run. None is selected here. Both algorithms are repeated in both sampling-seed slots; Borůvka ignores the seed, providing a replication/control check. Each size has `Iterations(2)->Repetitions(3)`, one certified warmup before each callback, and a reset to the same sampling seed on every KKT invocation. Consequently repetitions measure timing variation for a fixed graph/stream; they are not six independent KKT random samples.

Counts: 3 families × 2 algorithms × 2 graph seeds × 2 sampling seeds = **24 processes/curves**; 264 distinct size instances; 792 callback/repetition records; **1,584 timed calls and 792 warmups** (2,376 raw rows); 792 independent reference certificates. There are 24 built-in BigO/RMS pairs (48 aggregate records), plus the library's ordinary repetition summaries. Each built-in curve uses all 33 repetition means, each the mean of two calls, not eleven graph medians. Exact JSON schemas/counts require verification against the built library before freeze.

Keep matching hierarchy/shuffled graph seeds and every size/loss. Check weighted fingerprints across algorithms and sampling slots, and topology fingerprints across twins. Use ascending sizes for graph slot 0 and descending for graph slot 1. Enumerate families, then graph slot, then sampler slot; reverse the two algorithm blocks when `(graph_slot + sampler_slot)` is odd. Record the literal process schedule. This balances simple position effects but size direction is confounded with graph realization and each algorithm's whole ladder remains contiguous. It is **not** the six-position paired ranking protocol. Clock drift, memory history and thermal drift can still affect a curve; no causal algorithm-ratio claim follows from this order alone.

## Timing and correctness boundary

`current_complexity.cpp` includes the unchanged six-solver harness with `KKT_RETENTION_HARNESS_NO_MAIN`, reusing its fixtures, fingerprint, independent Kruskal reference, cycle certificate, checked warmup and comparator. Its measured lambda preserves the original public tuple-input boundary: construct `problem`, invoke the solver and destroy that temporary input. Returned result checking/destruction, graph generation, oracle, certificate, raw-output I/O and metadata are outside the manual clock interval. The Google Benchmark CPU timer is paused before result checking/destruction and resumed only afterward.

Every timed/warmup output must equal the independently certified unique-weight MST ID set. Steady elapsed time, process-CPU endpoints and UTC endpoints are recorded for every call; wall reversals are retained and flagged by the future collector, never silently discarded. `UseManualTime` receives the steady interval. `MeasureProcessCPUTime` asks the library to measure process CPU. Its CPU interval also contains a small amount of loop, clock-reading and pause/resume machinery; it is **not exactly** the separately recorded process-CPU envelope. No graph generation or result validation is allowed in either claimed solver boundary.

## What version 1.5.2 actually fits

The pinned [complexity implementation](https://raw.githubusercontent.com/google/benchmark/v1.5.2/src/complexity.cc) tries constant, log₂N, N, Nlog₂N, N² and N³ models. For each g(N), it fits a zero-intercept coefficient `c=Σ(tg)/Σ(g²)` and reports `sqrt(mean((t−cg)²))/mean(t)`. This is least squares of absolute residuals, followed by normalized RMS reporting; it is not equal weighting of relative pointwise errors. `oAuto` chooses the CPU-time model and fits manual/real time to that same selected model. Large absolute-duration residuals can dominate the selection.

The pinned [runner](https://raw.githubusercontent.com/google/benchmark/v1.5.2/src/benchmark_runner.cc) substitutes supplied manual time for real time while retaining measured CPU time. Explicit iteration counts avoid adaptive calibration; all successful repetitions are collected for complexity fitting. The [timer/state implementation](https://raw.githubusercontent.com/google/benchmark/v1.5.2/src/benchmark.cc) starts timing upon loop entry and supports pausing validation. The [public header](https://raw.githubusercontent.com/google/benchmark/v1.5.2/include/benchmark/benchmark.h) supplies the APIs used here. These are source-reviewed facts, not a claim that a local 1.5.2 library has been built or validated.

Preserve the built-in label, coefficients and RMS verbatim. Independently reconstruct all six fits from the 33 exported repetition means for both library clocks, checking the built-in choice/numbers. Also form the same 33 two-call arithmetic means from the separately recorded steady and process-CPU samples and fit those clocks independently, publishing all six models, coefficients and residuals. Predetermine the full eleven-point window and the upper six sizes (32,768 through 1,048,576); do not choose a favorable window afterward. For each graph/sampler curve, show per-size median and all six raw calls, T/N, adjacent-size slopes and descriptive log-log slope. Report individual realization fits, not just a pooled model. A finite range can make N and NlogN hard to distinguish, and neither an automatic label nor an empirical exponent proves expected O(m+n). Two graph seeds and two sampling seeds also do not establish a general expectation over all random choices.
