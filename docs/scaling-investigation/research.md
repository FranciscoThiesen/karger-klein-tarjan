# Why linear expected work can produce an N log N runtime fit

Research and source assessment, 2026-10-15. This note proposes diagnostics and isolated changes; it reports no new native performance result. The baseline is the experimental retained-parallel, Edge-view, compressed-query, private p=1/8 KKT implementation used by the completed [current-complexity study](../../benchmark/results/current-complexity-2026-10-15/README.md). Production changes and diagnostic instrumentation being developed in this worktree must be identified separately from that frozen binary.

The immediate objective is to explain the increase in time per represented input, then improve the responsible phase. Making a model selector print `N` is not an optimization target.

## What the existing result does and does not establish

The completed experiment selected `NlgN` for all 24 Google curves and all 192 custom curve/clock/window combinations. It retained every input and clock, with independent arithmetic validation. That result is meaningful evidence of finite-range growth; it does not identify a source-code loop or an asymptotic lower bound.

Google Benchmark v1.5.2 compares only six one-parameter, zero-intercept functions: 1, log N, N, N log N, N² and N³. Its implementation minimizes squared duration residuals, then normalizes RMS by mean time; the comment saying “relative error” does not make this a per-point relative-error objective. Library CPU chooses the model and manual time uses that same model. Larger-duration observations therefore have substantial influence. [Pinned implementation](https://raw.githubusercontent.com/google/benchmark/73d4d5e8d6d449fc8663765a42aa8aeeee844489/src/complexity.cc).

An analytic illustration, not a fit to new data: the local log–log slope of N log N is `1 + 1/ln N`, about 1.06–1.07 over N≈10⁶…3.5×10⁷. A finite-range N^1.13 curve can still choose `NlgN` from this coarse menu. The previously reported upper-window KKT slopes of roughly 1.13–1.16 consequently should not be described as an exact N log N shape. A cache transition, changing operation mix, allocation behavior, or a combination could produce a similar menu choice.

The original KKT guarantee is expected work on a unit-cost RAM with randomized sampling and linear verification. It is not a guarantee of constant nanoseconds per RAM operation on a finite machine. [Karger, Klein and Tarjan, 1995](https://www.cs.cmu.edu/~guyb/paralg/papers/KargerKleinTarjan95.pdf). For our retained-parallel variant, the separately audited recurrence and primitive implementations remain the relevant proof obligations; the original paper is not a substitute for them.

The next analysis should preserve the existing labels and add explanations. For each phase, report its relevant work quantities per N and time per work unit. Do not sum the 65 counters into a fictitious instruction count: several overlap, and a vertex visit, hash insertion and copied edge have different costs. A stable phase operation mix is needed before interpreting `T/W` as cost per operation.

## The verifier search is not an obvious hidden logarithm

The loop in [compressed_tree_path_maxima::visit](../../verifier/experimental_compressed_queries.hpp) performs a binary search over a set of path-state bits. Its worst individual search can grow with tree height. That alone does not make total verification superlinear. Hagerup's original chapter states linear tree-path-maxima verification; authored lecture treatments explain the fully branching reduction and its amortization. [Hagerup, WG 2009](https://link.springer.com/chapter/10.1007/978-3-642-11409-0_16), [Zwick's notes](https://www.cs.tau.ac.il/~zwick/grad-algo-0910/mst-verify.pdf), [Assadi, §4.3, Lemma 11](https://sepehr.assadi.info/courses/cs860-w24/Lectures/lec1.pdf). The original chapter's full text was not available in this review; the following is our source-specific derivation.

Let L be the number of equal-depth leaves and Q the logical proper-ancestor requests in one connected verification call. The actual caller requests only original vertices, which are leaves of the full branching tree. Every internal node has at least two children. For a vertex v let q_v count requests originating in its subtree. `init` unions descendant request masks and deletes expired depths, so its mask has at most q_v bits. `down` selects at most one path-state predecessor per requested depth. The median table halves the remaining bit ranks, giving O(1+log₂(1+q_v)) search work.

At distance i above the leaves, the number t_i of vertices is at most L/2^i and the sum of q_v is at most Q. Concavity, and monotonicity of `t log(1+Q/t)`, bound the level's logarithmic term by

`(L/2^i) log₂(1 + Q·2^i/L)`.

Since `log₂(1+a·2^i) ≤ log₂(1+a)+i`, summing levels gives O(L + L log(1+Q/L)) = O(L+Q). Constant search overhead is also linear in the tree size. Local request enumeration costs U≤Q. This argument depends on the actual fully branching structure; it is not a bound for arbitrary unbalanced trees merely accepted by a generic helper.

Two other apparent logarithms have corresponding size reductions. The median lookup has 2^(h+1) entries, at most 2L for height h. The [LCA](../../lca/lca.cpp) sparse table covers Θ(t/log t) Euler-tour blocks, so its block-count-times-logarithm term is O(t), not O(t log t). Its microtables are also bounded by the chosen half-log block size. These arguments assume the supported word/mask domain and valid tree inputs. Measure `path_binary_search_steps`, `median_entries`, `lca_sparse_cells` and `lca_micro_cells` directly to check finite constants; the proof does not say they are cheap.

A conservative prospective accounting gate is `path_binary_search_steps <= 4*fbt_input_vertices + 3*verifier_queries`, summed over connected verifier-tree calls. The extra tree-size term covers ceiling effects in each halving search: `ceil(log₂ k) <= 1+log₂(1+q_v)`, and `2/ln 2 < 3`. This is an upper-bound check, not a prediction of observed comparisons. The accompanying [source audit](source-audit.md) also gives the deterministic recursion-volume bound, separately from the randomized expected-linear bound.

## An explicit expected edge-volume budget for p=1/8

Let the original graph have n vertices and m edges, and let M and V sum edge and vertex inputs over **all recursive KKT calls**. For a call with v vertices and e edges, the two retained contractions produce q≤v/4 vertices and r≤e edges. Every surviving contracted component contains at least two preceding nonisolated vertices; isolated components are removed. This remains true when the graph is disconnected. Subsequent sample/filter normalization only removes vertices, so the two children together have at most v/2 vertices. Consequently V≤2n deterministically.

Condition on the current quotient before its fresh ideal independent Bernoulli-p sample. Its expected sample edge count is pr, and the expected F-light survivor count is at most q/p, even for parallel edges and disconnected sampled forests. One way to see the latter: process edges in unique increasing weight order. Whether an edge is F-light depends only on earlier sample decisions; its own inclusion is independent. The sampled F-light edges are precisely the sampled MSF, with at most q−c edges for c components of the quotient. Thus `p E[light] = E[|F|] ≤ q−c ≤ q`. Removed sample isolates do not change that forest when lifted back to the quotient. This is the conditional form of the [KKT sampling lemma](https://www.cs.cmu.edu/~guyb/paralg/papers/KargerKleinTarjan95.pdf).

Therefore expected child edge volume is at most `p e + v/(4p)`. Summing over the recursion tree and using conditional expectation gives

`E[M] ≤ m + p E[M] + E[V]/(4p) ≤ m + p E[M] + n/(2p)`.

The deterministic logarithmic-depth/finite-volume bound in the source audit justifies taking these expectations and summing the calls. At p=1/8,

`E[M] ≤ (m+4n)/(1−1/8) = 8m/7 + 32n/7`.

Each call's first and second contraction inputs total at most 2e, including terminal calls where the second is omitted. Hence the expected sum of **contraction input edges** is at most `16m/7 + 64n/7`. These correspond to `kkt_edges` and `contraction_edges`; the latter is not the multi-pass `contraction_edge_visits` counter.

These are ideal-sampling expectations, **not per-seed hard gates**, timing bounds or memory bounds. They require an exact sampled MSF, valid loop-free input with unique ordering, and conditionally fresh independent coins at every node. A single ideal infinite random stream has fresh unused suffixes after terminating recursive calls; a deterministic MT19937 seed is an implementation approximation to that probability model, not a proof of independence or a guarantee that its realized counters satisfy the expected budget.

## Source-grounded suspects, ranked before hardware speculation

The current source contains several mechanisms that can be changed independently of sampling policy.

The connected fast path skips this preparation. | Attribute time and bytes separately to the wrapper and connected verifier. Replay the same `(G,F)` connected/disconnected snapshots. The disconnected path already has stronger support than a generic cache hypothesis: the completed [lower-density work report](../../benchmark/results/lower-density-2026-10-15/work/README.md) isolates substantial extra partition scans and proves one large root uses the disconnected branch. That is a work-count explanation for that counter difference, not evidence that the same branch explains every Google curve or a particular fraction of CPU time.

## Ideas worth borrowing, with their limits

**Practical MST filtering favors regular independent queries.** Katriel, Sanders and Träff use Prim order to turn sampled-tree path maxima into interval maxima, with a small number of independently executable lookups per edge. Their I-Max-Filter is a different algorithm with O(m+n log n) expected work, not this KKT implementation. [Primary paper, §§2–3](https://ae.iti.kit.edu/documents/people/sanders/papers/filter.pdf). The immediate borrowing is to batch independent LCA/lookup work and reduce indirection. A full interval-filter alternative is a larger comparator/algorithm experiment: obtaining Prim order and building its tables must be charged. Do not assume arbitrary DFS order gives the same path-maximum identity.

**Filtering can be cheaper than fully organizing all records.** Filter-Kruskal partitions by a weight pivot, solves the lighter side, then discards heavier edges internal to the resulting components before processing the rest. [Osipov, Sanders and Singler, algorithm and implementation](https://ae.iti.kit.edu/documents/teaching/algorithm-engineering/ss22/fkruskal.pdf). This suggests examining the cost of stable selection/compaction, not installing a sort or a hash table at every recursive step. Filter-Kruskal itself is a different algorithm; its random-weight analysis does not establish a KKT bound or a result for ordered attachments.

**Data movement is a separate model.** External-memory connected-components experiments include a tuned KKT-style method competitive on several workloads, while changing the cost model and objective. [Brodal et al., SEA 2021](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.SEA.2021.23). The transferable idea is to organize operations into scans and compact batches. Their disk-I/O results are not weighted RAM-MST evidence, and a sort introduced to improve locality would need its own work/cost accounting.

**Low bandwidth does not rule out a memory bottleneck.** Beamer's graph-workload study separates independent requests, instruction-window limitations, translation and attained bandwidth. It uses multiple pointer chains to vary memory-level parallelism and shows translation effects on its measured Ivy Bridge system. [Author's dissertation, chapter 5](https://www.scottbeamer.net/pubs/beamer-thesis.pdf). Borrow the experiment design, not its cache sizes, Linux huge-page behavior or numeric limits. A load-dependent chain can stall while leaving most bandwidth unused; increasing independent requests can distinguish that from saturated transfer bandwidth.

**Use separate latency and bandwidth calibration.** STREAM measures sustained contiguous-array transfer behavior; lmbench varies dependent-load footprint and stride. They answer different questions. [McCalpin's STREAM](https://www.cs.virginia.edu/stream/), [McVoy and Staelin's lmbench, §6](https://www.usenix.org/publications/library/proceedings/sd96/full_papers/mcvoy.pdf). Lemire supplies a small independent-chain experiment and code useful as a starting point, with explicit measurement limitations. [Author's experiment](https://lemire.me/blog/2018/11/05/measuring-the-memory-level-parallelism-of-a-system-using-a-small-c-program/). An Apple-specific calibration must be measured afresh. A streaming ceiling cannot by itself predict KKT throughput.

**Allocation policy can change locality as well as allocator time.** Mimalloc's page-local free-list design explicitly targets locality and allocation fast paths. [Leijen, Zorn and de Moura, technical report](https://www.microsoft.com/en-us/research/publication/mimalloc-free-list-sharding-in-action/). This supports a controlled allocator/arena ablation after observing allocation sizes and lifetimes. It does not establish that replacing the macOS allocator will help here. A scratch arena should release at a proved lifetime boundary, avoid retaining parent buffers unnecessarily, and report peak retained capacity.

**Hardware evidence should distinguish reasons for stalls.** Apple's Instruments guidance separates profiling from CPU-counter bottleneck analysis. Processor Trace in that guidance requires M4/A18-class hardware and should not be assumed available on the measured M3. [Apple, WWDC25 CPU performance session](https://developer.apple.com/videos/play/wwdc2025/308/). Verify tool/event availability before promising a cache/TLB profile. If counters are inaccessible, retain that limitation and use intervention results without relabeling them measured cache misses. Drepper's memory hierarchy exposition is useful background for cache/translation experiments, but its historical x86 numbers are not Apple calibration. [Author's paper](https://www.akkadia.org/drepper/cpumemory.pdf).

## A small orthogonal investigation, not another family search

1. **Match the existing workload first.** Collect the 65 logical counters, exclusive phase times, allocation counts, requested/usable bytes and live high-water mark for selected existing small/middle/large inputs. Preserve fingerprints and MST IDs. Phase instrumentation is a diagnostic build: transition clocks and allocation hooks perturb execution, so final performance comes from an uninstrumented paired build. Timing total should reconcile with phase accounting; instrumented phase shares are not automatically uninstrumented CPU shares.

2. **Separate amount of work from its unit cost.** Plot each important phase's counts/N and time/relevant-count, retaining all seeds. Record connected/disconnected call counts, not only totals. Stable work/N plus rising time/work makes a machine-cost explanation plausible. Rising work/N points first to recursion composition or representation work. Both can occur together. Correlated counters cannot identify unique per-operation cycle costs by an unconstrained regression.

3. **Replay one exact phase input.** Serialize or deterministically rebuild selected `(G,F)` verifier inputs and contracted graphs outside timing. Compare original layout, contiguous adjacency, and batched query traversal using the same marks and MST certificate. Include setup in an end-to-end comparison; a prepared replay isolates the kernel but does not replace total solve timing. Avoid regenerating a different random forest when changing query layout.

4. **Vary footprint without changing the mathematical problem.** On a fixed replay, change only address layout or additional controlled live storage, then sweep around observed transition regions. Compare sequential accesses, endpoint gathers, one dependent chain and several independent chains. Check page size, page faults and RSS separately; a stride experiment is not a pure TLB experiment because it also changes cache behavior. Avoid unsupported huge-page or cache-flush assumptions on macOS.

5. **Isolate lifetime, allocation and initialization.** First shorten lifetimes without reusing buffers. Separately test reuse without changing contents, then representation changes such as CSR. Never skip required initialization merely to make the profile smaller. An allocator-only replay can hold allocation sizes/order constant, but does not capture the locality of subsequent graph operations. Pair it with the full solve and report both outcomes.

6. **Break the existing order confounding.** Repeat the same graph in both ascending and descending size order, or a declared randomized block schedule, in separate processes. The previous two graph seeds are confounded with traversal order; sampler labels do not provide four independent Borůvka inputs. Use enough process repetitions to see process/allocator state, instead of spending all repetitions inside one process. Hierarchical repetition is a standard way to locate the dominant variance level. [Kalibera and Jones, corrected author manuscript](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf). Historical demonstrations also show that innocuous execution-layout changes can bias comparisons; they motivate controls, not a claim of this failure here. [Mytkowicz et al., author-institution record](https://research.ibm.com/publications/producing-wrong-data-without-doing-anything-obviously-wrong).

7. **Use prediction to assess explanations.** Keep the original six-model output. For new exploratory models, preregister a small set such as affine-linear time, a phase-work model, and a footprint-transition model, then evaluate on held-out sizes/orders. Show residuals and adjacent doubling ratios, including nonmonotone points. An intercept or extra breakpoint will almost always improve training fit; the question is whether a separately measured mechanism and held-out behavior support it. Do not discard the small points or retrospectively pick a winning window.

## Implementation order and correctness boundaries

Start with (a) shorten dead local-buffer lifetimes, then separately consider reservation policy if excessive live capacity remains; (b) remove vector-of-vector allocation in an important measured phase; and (c) avoid copying/remapping the full query graph on the disconnected verifier path. Do not combine these into one change. They are orthogonal to changing the sampling probability. Batched LCA/gather work follows if dependency/working-set probes support it. A wholesale new MST filter or adaptive sampling policy is a separate study, not necessary to explain the current fit.

For representation-only changes, require exact selected IDs, heavy marks by input position, RNG engine states/word counts, recursion-input identities and unchanged unaffected work counters. Verifier-helper tests must preserve its legacy loop and repeated-external-ID behavior, alongside disconnected forests, isolates and supported negative/extreme weights. Full KKT differential tests must stay within its loop-free, distinct-ID, uniquely ordered valid-input contract and retain the independently certified generated inputs. Shortened lifetimes must preserve public input ownership. Reordering graph records can change which random word an edge receives; either prove the same sampled-edge sequence or classify the experiment as a changed random realization. Relabeling can also change traversal/numbering, so verify invariants rather than assuming it is a pure layout change.

Keep all six solvers in a final end-to-end performance comparison, with the same public result and construction/destruction boundary. A phase improvement may be useful while the whole program still fits `NlgN`, and a flatter normalized curve may still lose in absolute time. The useful conclusion is a verified reduction in cost with an explanation that survives controls, not a preferred asymptotic label.
